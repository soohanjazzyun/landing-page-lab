# Task A: three independent UpdateShelf hero directions

## landing-page-story

**Headline:** Turn Markdown release notes into a page you can share.

**Supporting sentence:** Paste your notes into UpdateShelf, preview the formatting, and publish an update with its own URL.

**CTA:** Preview an update

**Rationale / tradeoff:** Leads with the input, the output, and the steps connecting them, repairing the current hero’s basic explanation gap. It explains the product clearly but gives less prominence to the solo developer’s existing writing habit or the preview decision.

## landing-page-resonance

**Headline:** Give the release notes you already wrote a page of their own.

**Supporting sentence:** If you ship a paid developer tool solo, paste your Markdown into UpdateShelf to preview and publish an update for your current users.

**CTA:** Preview an update

**Rationale / tradeoff:** Opens at the supplied audience’s recognizable moment: the notes already exist, and current users need a readable page. It makes that use case more prominent while leaving editing after publication out of this short hero; this is a relevance hypothesis, not evidence of demand.

## landing-page-offer

**Headline:** See how your release notes will read before you publish.

**Supporting sentence:** Paste your Markdown into UpdateShelf to preview one formatted update, then publish it with a shareable URL when you choose.

**CTA:** Preview an update

**Rationale / tradeoff:** Makes the next commitment concrete: supply existing Markdown and inspect the preview before publication. It emphasizes the first useful result over the final published artifact, without assuming a price, account requirement, timing promise, or functioning CTA destination.

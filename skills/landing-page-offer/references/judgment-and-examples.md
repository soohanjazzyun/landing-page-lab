# Offer judgment and examples

Use when a page sounds attractive but the next commitment remains hard to judge. These are fictional editorial examples, not measured outcomes.

## Copy fixes versus business changes

| Finding | Can change in a presentation pass | Requires a separate business/product decision |
|---|---|---|
| A local tool's button says “Start instantly” | Name the real install or quickstart action and list prerequisites | Build a hosted trial |
| A service's scope is buried | Move the supplied deliverables and limits beside the purchase decision | Add implementation work to a consultation package |
| No customer proof exists | Show an inspectable example and explain its provenance | Promise a result, invent a testimonial, or imply certification |
| Setup looks unclear | Explain the actual steps and required inputs | Remove permissions or automate work the product does not handle |
| Pricing was not supplied | Omit invented figures and record the open decision outside copy | Choose a price or advertise a discount |
| The founder asks for offer alternatives | Present feasible options with costs and dependencies | Treat an option as approved or available |

Recommend the smallest change that answers the real hesitation. A more prominent price does not fix unclear deliverables; more features do not fix an unsupported result. Do not conceal effort just because the shorter promise reads better.

## Match certainty to evidence

An example output can show what a tool produces. It cannot establish typical accuracy, time savings, or business impact. A refund policy can reduce financial exposure only within its actual conditions; it cannot prove the product works. A relevant founder background can establish experience without proving every user's outcome. A local install can avoid a hosted account without proving that no dependency sends data externally.

When comparing a current alternative, use documented costs and steps in a stated situation. Do not invent competitors' limitations, multiply hypothetical hourly savings into a large value total, or treat list prices as demonstrated buyer value.

## One source, a different page decision

Fictional facts: **Turnlist** reads a Markdown checklist and generates a static HTML status page locally. No hosting, sync, task assignment, price, timing benchmark, or customer proof was supplied. The founder chose solo maintainers.

A story pass explains the input/output. A resonance pass chooses a familiar release-checklist situation. An offer pass makes the next commitment tangible:

> **A static status page from your Markdown checklist.**
>
> Turnlist is a local CLI that generates an HTML file from your checklist. Inspect an example, then follow the quickstart to generate your own. You handle hosting; there is no shared workspace or task assignment.
>
> **Read the quickstart**

Use that CTA only if a real quickstart destination exists. Put actual runtime requirements from the source beside it. If the command or example was not supplied, specify an asset to create and verify rather than fabricate a runnable command in the copy.

The main decision is the first useful result: an inspectable HTML file. “A live team dashboard in 30 seconds” would introduce hosting, collaboration, and a timing promise absent from the source. “Never pay for project management again” would promise broader replacement and savings not established by a file generator.

## When exploration is requested

For the same tool, an owner might consider adding a browser-based example preview. Present this as a proposal: it could reduce the need to install before understanding the output, but someone must build, maintain, and verify it. It does not create hosted user workspaces. Keep the current page accurate until the preview exists. Prefer a small observable check, such as whether readers can identify the output and prerequisites, over an invented conversion forecast.

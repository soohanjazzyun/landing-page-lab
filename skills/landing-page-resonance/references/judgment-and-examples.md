# Audience judgment and examples

Use this reference when narrowing an audience would materially change the promise, example, or action. All examples below are fictional editorial examples, not customer research or performance evidence.

## Distinguish relevance from decoration

“For founders” pasted onto an unchanged generic page does not establish relevance. Ask what those readers are doing when they need the product, what they already use, and which documented constraint matters. If none of the copy decisions change when the audience changes, the proposed audience may be too vague or the available evidence too thin.

Do not narrow solely because a smaller label sounds sharper. Two audiences can share the same task, priorities, and adoption path. A single use-case page can serve both. Split the message when their desired result, required capabilities, proof standard, or next action diverges. Respect a deliberately chosen multi-audience page and explain the ordering instead of deleting an audience.

## Work with beliefs cautiously

| Available evidence | Reasonable use | Overreach |
|---|---|---|
| A user says they keep release work in Git | Show the repository workflow | All developers dislike dashboards |
| Product runs locally and exports HTML | Explain the local file workflow | “Private by design” without inspecting dependencies or data flows |
| Founder wants to serve solo maintainers | Draft for that audience | Claiming maintainers asked for this product |
| Three interviews mention a setup obstacle | Report that obstacle with the sample limit | Presenting it as the whole market's dominant problem |
| No customer evidence exists | Offer an explicit message hypothesis and a check | Inventing a quote to sound empathetic |

Separate a useful preference from a flattering identity. “Keep the checklist in the repo you already maintain” names behavior. “For serious builders who refuse busywork” assigns superiority and offers little information.

## One source, three genuinely different decisions

Fictional product facts: **Turnlist** is a CLI that reads a Markdown checklist and generates a static HTML status page locally. It does not host, sync, or assign tasks. The founder chose solo maintainers. No price, timing benchmark, or customer proof was supplied.

- A clarity pass could lead with “Generate a status page from a Markdown checklist,” then show the input and output. Its main decision is explaining the mechanism.
- This resonance pass could lead with “Your release checklist already lives in the repo. Give it a status page.” The next line identifies the CLI and local HTML output. Show a release checklist rather than a generic team dashboard. Explain that maintainers keep the Markdown source and handle hosting themselves. Its main decision is a recognizable occasion and a meaningful fit boundary.
- An offer pass could lead with the exact artifact the reader receives, show the real command and generated file, and place local setup and self-hosting requirements beside “Read the quickstart.” Its main decision is making the trial commitment evaluable.

The resonance draft assumes a repository-based release habit. Mark that as a working interpretation unless supplied by the source. If the founder instead says the audience maintains personal checklists outside Git, change the occasion rather than preserving an attractive but unsupported line.

## A useful disconfirmation plan

Show the same factual draft to a few intended readers without telling them the desired interpretation. Ask what task they would use it for, which line sounds familiar, and what would stop them. Compare reactions from a nearby but less suitable group only when it helps test the boundary. If both groups misunderstand the product category, fix explanation first. If they understand it but reject the value or requirements, preserve that finding instead of polishing the language indefinitely.
